Opem Amalur — explicit recovered-module loading candidate

Files in this staging directory do not modify the frozen v0.5 reconstructor or
the v0.6 portable source. amalur_runtime.c/h are proposed v0.7 runtime copies.
Parent workflow performs all compilation and fresh execution on Windows.

The portable implementation uses stock Lua5.1 require/module behavior with a
preload-only private searcher. Each module is explicitly registered by trusted
host code using a name and source buffer or file. Original registration APIs
compile but do not run the chunk; separate *_lazy APIs retain the explicit
filename or a Lua-owned copy of source and compile only on require. Lazy syntax
and file errors are intentionally deferred. File contents must stay unchanged
until loading; the API itself provides no file hash or snapshot guarantee.
Dependencies run when require reaches them and share the
evaluation's instruction and memory budgets. The public package interface has
loaded and seeall only; no filesystem or dynamic-library search path is used.
This does not establish that every native Amalur module-loading edge is identical.

Module tables
Lua5.1 module(..., package.seeall) installs __index=_G on its module table. The
v0.5 generated field guards rejected all metatables, so valid module field reads
would otherwise fail. module_source_adapter.py opt-in adapts only generated
field/table read and write guards. Length/list/key/custom-type restrictions are
unchanged. The public getmetatable function is untouched.

The host records seeall tables only when their name has an explicit source
registration and their _M identity matches the loaded module. A field access is
admitted only while the marked metatable is still the same object and contains
exactly __index=_G. Arbitrary lookalike metatables, replaced metatables, added
metamethods, and altered __index values are rejected. Other metatable behavior
remains unsupported. This is an admitted semantic domain, not a security sandbox.

Corpus selection
export_scene_modules.py starts from SpaceCommon by default, using existing
standalone names and frozen v0.5 whole-script/IR files. It conservatively follows
literal require arguments within individual IR basic blocks. Unresolved dynamic
requires, names absent from the standalone index, and ambiguous name variants
are reported. It does not guess archive precedence or invent missing modules.
Original and adapted source digests are recorded for every selected module.

APK bootstrap
Config accepts runtime_sources/count: exactly five fixed bootstrap basenames
with borrowed bytes/lengths. The host opens assets before create and closes them
after create returns, including failure. Runtime retains none of these pointers.
This mode never falls back to runtime_dir. Zero-initialized config retains the
directory-based behavior. Recovered module assets use the source_lazy API, which
copies bytes into the capped Lua allocator. This avoids filesystem extraction.
It does not implement asset manager code or Android installation itself.

Shared scene bootstrap
scene_script_bootstrap.c/h supplies shared Windows/APK loading logic. The host
implements size and exact-read callbacks for logical runtime/ and modules/
resources. The function parses the explicit manifest, rejects path traversal,
duplicate names and excessive counts, preflights every source length, creates
the runtime from five in-memory bootstrap sources, lazily registers copied
module source bytes, then requires the root and optionally invokes a zero-arg
event. It returns the live realm to its caller on success. On failure it destroys
the realm and frees all C buffers; source copies use the capped Lua allocator.
The result preserves phase/error, module count, byte totals and event status.
No provider state is invented. Limits default to1MiB manifest,16MiB/source,
64MiB total resource bytes, and the runtime's64MiB Lua cap. Resource byte and Lua
allocator limits are separate; an honest memory failure remains possible.

Compile scene_script_inspect.c and scene_script_bootstrap.c with amalur_runtime
for the directory-backed Windows front end. Compile scene_script_bootstrap_test.c
and scene_script_bootstrap.c with amalur_runtime for synthetic shared-logic tests.
The test accepts RUNTIME_DIR. Inspector accepts --runtime-dir DIR --modules-dir
DIR [--module NAME] [--event NAME] [--memory-mib N]. Android can use this same bootstrap function
with AAsset size/read callbacks; reader code must verify unchanged length.
The optional options.setup callback runs protected after core initialization,
before recovered modules. It is for explicit trusted host integration; it has
no automatic providers and does not bound arbitrary native host work.

Ownership review: the shared bootstrap frees its manifest, source scratch buffers
and core buffers on all inspected success/error paths; lazy source registrations
copy into Lua memory. Failures destroy the partial realm; successful return gives
realm ownership to the caller. Android's current one-shot hook destroys it after
logging. All inspected AAsset handles close. Source strings remain retained by
lazy loader closures, so Lua memory includes both retained text and compiled
chunks. The Lua cap is not a whole-process RSS limit. Asset I/O and compilation
are not Lua instructions and therefore are not bounded by the instruction hook.
The hook currently precedes rendering/input setup on its worker; device startup
and teardown latency has not been measured.
